# 评委问答准备（25 条）

> 原则：不夸大、不编造；每个结论尽量给证据（trace、评测、代码/演示）。
> 不要自称“全自动 Agent”，准确说法是“human-in-the-loop 消费健康 Agent”。

## 1. 为什么不是又一个记账 App？

因为记账只解决“记录”，我们解决“下一步”。知账把记账、预算、订阅、目标串成多步任务，写操作先出 diff、用户批准才执行，执行后可撤销、可审计。竞品大多停在记录或单轮问答。

## 2. 这算 Agent 吗？还是规则？

混合式 Agent：模型只负责账单自然语言解析；查询/订阅/目标的数字由规则/SQL 计算，回答用模板；工具注册表负责执行，状态机负责审批。现场可以换一个输入、拒绝一次审批、修改一次金额，证明不是固定模板。

## 3. 为什么不做多 Agent？

时间紧、任务边界清楚。单 Agent + 状态机更容易调试、审计、控成本；多 Agent 在演示里增加不确定性，不增加可验证价值。等任务复杂度上来再拆。

## 4. 数字会不会是模型编的？

不会。余额、预算、订阅、目标、年化影响全部由 SQL/Python 计算，模型只拿到聚合结果并组织语言。每个结果带 `source` 和 `as_of`；现场可以改一笔账重算。

## 5. 每次都要审批，会不会很烦？

只对写操作审批，查询不审批。审批卡展示 diff、影响金额、来源；可以“批准/拒绝/修改”。高频低风险动作后续可以加“记住选择”，但资金相关动作默认保留审批。

## 6. 重复点击批准会重复写吗？

不会。审批状态用条件 UPDATE 原子占用（`WHERE status='pending'`），重复/并发批准只有一个请求能执行；`idempotency_key` 唯一。`tests/agent_smoke.py` 有“重复批准不重复写账单”和“过期审批不能执行”的断言。

## 7. 撤销怎么实现？

执行时把反向操作写入 `diff.undo`：删账单、恢复预算、删目标/任务、恢复订阅状态。撤销按逆序执行，标记 `undone`，并写审计步骤。现场可以演示。

## 8. 用户拒绝后怎么办？

订阅场景有替代方案：拒绝“暂停”后，Agent 改为“先观察一个月 + 复盘任务”，生成新的审批；不是重复原方案。其他场景没有替代方案就取消，不写任何数据。

## 9. 模型挂了怎么办？

账单解析自动降级为规则解析；查询/订阅/目标本来就不依赖模型。AI 未配置/超时/限流时，返回可读提示或规则结果，不阻塞记账、预算、便签等主功能。

## 10. 单次成本多少？

账单解析用轻量模型，单次约 ¥0.002（按当前模型估算）；查询/订阅/目标走 SQL，成本接近 0。每用户每日限流 30 次；后续加模型路由和缓存。

## 11. 延迟多少？

查询 <100ms；订阅/目标 <100ms；账单含模型解析约 2–11s。60 条评测平均 1.56s，P95 7.46s。现场网络差时用规则降级或录屏兜底。

## 12. 隐私怎么保证？

只用合成演示数据；敏感数字先脱敏；日志不含密钥；音频转写后删除；不接真实银行账号；写操作审批 + 审计。正式上线前补隐私政策、同意、删除/导出、境内存储。

## 13. 语音精灵呢？

P1 增项：按住说话 → ASR → 复用现有记账解析 → 草稿确认。不做唤醒词/后台持续监听，避免隐私和功耗问题；识别失败可一键切文字。

## 14. 订阅暂停真的能取消第三方服务吗？

不能，也不承诺。我们只改站内订阅状态、停止自动记账和提醒，并创建复盘任务；不代替用户取消第三方平台服务。这是合规边界。

## 15. 为什么选消费不是金融？

消费健康/预算管理更贴近真实用户，也避开投资建议、代客理财、自动转账等金融合规风险。我们把“金融”能力限定在预算、储蓄目标、订阅支出，不做投顾。

## 16. 和支付宝/微信/随手记/Copilot/Rocket/Monarch 有什么不同？

支付宝/微信强在支付入口，随手记/鲨鱼强在记录，Copilot/Rocket 强在单用户审批/订阅行动，Monarch 强在家庭数据和权限。我们的空位是：中文跨平台家庭账单 + 多步行动 + 审批/审计 + 可解释轨迹。

## 17. 用户从哪来？商业模式？

先校园/初入职场人群，免费记账 + 家庭版订阅（多人、预算、Agent 高级能力）；再与校园/社区/银行合作做匿名聚合洞察。比赛阶段先验证任务完成率和留存，不夸大收入。

## 18. 冷启动数据从哪来？

三条路：手动/截图/自然语言；后续 CSV 导入微信/支付宝账单；再后续开放银行/账单 API。比赛演示用合成数据，避免隐私风险。

## 19. 怎么证明有效？

三层证据：60 条 Agent 自测（当前 60/60）、36 项执行/撤销/幂等断言、5–15 名用户可用性测试（任务耗时、SUS、访谈）。正式区域赛前扩到 100 条 + 更大样本。

## 20. 60/60 是不是过拟合？

有可能。评测集是我们自己写的，判定是启发式；我们在 `evaluation.md` 里明确写了局限。下一步加人工标注、换模型回归、用最终数据库状态做严格比对。

## 21. 失败案例是什么？

空金额/模糊请求会先澄清；AI 超时降级规则；跨用户返回 404；重复批准幂等；撤销恢复数据。现场可以演示“午饭”没有金额时的 needs_input。

## 22. 为什么不用向量数据库/RAG？

当前任务主要是结构化账单/预算查询，SQL 比向量检索更准、更便宜、更可解释。只有非结构化票据/政策文档才需要 RAG；时间紧时不引入。

## 23. 团队怎么分工？

角色：Agent/后端、前端/体验、产品/评测/材料。匿名材料只写角色，不写姓名/学校。每人有明确交付物和验收标准。

## 24. 下一步路线图？

校赛：100 条评测、10–15 用户、失败路径；区域赛：CSV 导入、家庭共享、成本面板、安全加固；国赛：现场可靠性、真实案例、商业合作。

## 25. 知识产权/开源合规？

代码为团队自研，使用开源库遵循许可证；不使用未经授权的素材；比赛材料匿名；第三方模型 API 按服务条款使用，不把用户数据用于训练。

## 26. 如果现场换一笔数据，会不会崩？

不会。可以现场改金额/商户/日期，Agent 重新解析并重算预算；如果金额缺失会先澄清。演示前用 `tools/seed_demo.py` 重置，现场改一笔不影响主流程。

## 27. 为什么不用端侧模型？

端侧模型在中文账单解析和复杂表达上还不稳定，且会让安装包变大。当前用云端 OpenAI 兼容接口 + 规则降级；后续可把分类/脱敏放端侧，敏感原文不出设备。

## 28. 如果评委说“这就是规则引擎”？

承认规则的存在，并说明分工：规则用于触发和确定性计算（这是优点，避免幻觉），模型用于理解/表达，工具用于执行，状态机用于审批。现场展示一个未见过的新输入 + 拒绝后重规划，比争论定义更有说服力。
